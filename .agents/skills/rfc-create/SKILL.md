# RFC 创建

为 xdiff 的新需求建立 RFC 文档。机制全文见 `docs/rfcs/README.md`，本技能内嵌执行所需的最小规则；两者冲突时以 README 为准。

## 何时需要 RFC

新功能、行为变更、架构调整等非 trivial 改动必须先建 RFC、再讨论、再开发。修 bug、格式化等保序的 trivial 改动不需要。拿不准时倾向于建——成本只是一份文档，而且它同时是对齐需求的工具。

## 步骤

### 1. 取编号

列出 `docs/rfcs/` 下所有 `rfc-NNN-*` 目录，取最大编号 +1，三位补零（当前最大 009 → 新编号 010）。编号全局唯一、永不复用——即使需求最终废弃（走 rejected），空号也不补。

### 2. 建目录与文件

- 目录名：`rfc-{编号}-{需求名}`。需求名为中文短语，用连字符分隔、不含空格，如 `rfc-010-托盘菜单`。
- 读 `docs/rfcs/_template/RFC.md`，按其结构在新目录下写 `RFC.md`。六个章节都要保留，暂时没内容的维持模板占位（`>` 引导语），后续阶段再填。

### 3. 填 front-matter

```yaml
---
id: 010                  # 与目录编号一致（三位字符串）
title: 托盘菜单           # 需求名，可与目录名里的短语一致或更完整
status: draft
created: 2026-10-29       # 今天
updated: 2026-10-29
---
```

### 4. 填正文

- **背景与目标**：为什么做、解决什么问题——取自用户描述里的动机，不要自行编造。
- **需求描述**：要做什么；验收标准写成可勾选清单（`- [ ]`），每条可独立验证。验收标准写不出来，说明需求还没想清楚，先回到用户对齐，不要硬凑。
- 其余四个章节（方案讨论 / 最终方案 / 实现记录 / 遗留问题）保留模板占位，由 rfc-continue 在对应阶段填写。

### 5. 收尾告知

完成后明确告诉用户：

- 当前状态 `draft`，只产出文档，不写任何实现代码；
- 下一步是讨论方案（可直接在本会话继续，或之后 `/rfc-continue`）；
- 建议提交信息：`docs(rfcs): 新增 {编号}-{需求名} RFC`（是否提交由用户决定）。

## 红线

- 不改 `_template/`，不占用已存在的编号。
- 正文一律中文（与项目规约一致）。
